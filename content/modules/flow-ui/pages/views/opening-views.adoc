= Открытие экранов
:page-aliases: opening-screens.adoc

Обычный (не корневой) экран можно открыть либо перейдя на его URL (указанный в аннотации `@Route`), либо на текущей веб-странице, открыв диалоговое окно.

При использовании навигации, URL веб-браузера отражает состояние пользовательского интерфейса приложения, что позволяет использовать _глубокие ссылки_. Пользователь приложения может скопировать и поделиться адресом URL, тем самым предоставляя ссылку на определенный экран и его текущее состояние, например, на сведения о конкретном экземпляре сущности.

Минусом навигации является относительная сложность передачи параметров в открываемый экран. Их можно передавать только в URL в качестве параметров {vaadin-docs}/routing/route-parameters[route^] или {vaadin-docs}/routing/additional-guides/query-parameters[query^]. Кроме того, невозможно вернуть в вызывающий код какие-либо значения из экрана после его закрытия.

При открытии экрана в диалоговом окне URL браузера не изменяется, но зато экземпляр открытого экрана доступен вызывающему коду. Он позволяет передавать любые значения непосредственно в экземпляр экрана и возвращать результаты после закрытия экрана. Этот подход используется при открытии экранов списков для выбора и возврата экземпляров сущностей в компонентах выбора.

Главное меню открывает экраны с помощью навигации. Стандартные действия xref:actions/list-actions.adoc#list_create[list_create] и xref:actions/list-actions.adoc#list_edit[list_edit] также открывают экраны деталей с помощью навигации, но их можно настроить на использование диалоговых окон. Стандартное действие xref:actions/entity-picker-actions.adoc#entity_lookup[entity_lookup] всегда открывает экран списка в диалоговом окне, чтобы иметь возможность вернуть выбранные сущности.

Ниже описывается, как программно открывать экраны в коде приложения.

[NOTE]
====
*Ограничения обратной навигации*

Обратная навигация поддерживает только один уровень вложенности экранов. Навигационный стек не сохраняет всю цепочку переходов между экранами.

В связи с этим ограничением:

* Экран, открытые из детального экрана, должны использовать режим открытия `DIALOG`.
* История навигации ограничена непосредственными отношениями родитель-потомок.
* Глубокие навигационные цепочки не могут быть восстановлены с помощью обратной навигации.
====

[[dialog-windows]]
== Открытие диалоговых окон

Бин `DialogWindows` предоставляет удобный интерфейс для открытия экранов в диалоговых окнах. Его терминальные методы предоставляют доступ к экземпляру открываемого экрана, что позволяет передавать входные параметры непосредственно в экземпляр экрана и добавлять слушатели для получения результатов из открываемого экрана после его закрытия.

[[dialog-size]]
=== Установка размера диалога

Существует несколько способов установить размер окна диалога:

. *Использование аннотации `@DialogMode`*
+
Добавьте аннотацию `@DialogMode` к классу экрана, который открывается как диалог. Это устанавливает размер по умолчанию для диалога при открытии экрана.
+
[source,java,indent=0]
----
@ViewController("MyOnboardingView")
@ViewDescriptor("my-onboarding-view.xml")
@DialogMode(width = "50em", height = "40em")
public class MyOnboardingView extends StandardView {
    // some code
}
----
. *Установка размера внутри открываемого экрана*
+
Вы можете изменить размер диалога из контроллера самого экрана. Это полезно, когда требуемый размер зависит от условий времени выполнения, например, от показа или скрытия полей.
+
[source,java,indent=0]
----
include::example$/onboarding/src/main/java/com/company/onboarding/view/myonboarding/MyOnboardingView.java[tags=onBeforeShow;set-size]
----
+
TIP: Метод `findDialog()` возвращает `null` , если текущий экран не открыт как диалог. Всегда проверяйте значение на `null` перед вызовом методов у возвращенного экземпляра диалога.
. *Установка размера при открытии диалога*
+
При использовании бина `DialogWindows` вы можете установить размер после построения окна диалога, но перед его открытием.

[[detail-window-builder-options]]
=== Дополнительные методы

`DetailWindowBuilder` и `DetailWindowClassBuilder` предоставляют дополнительные методы для интеграции открываемого экрана деталей с вызывающим экраном:

[cols="1,3",options="header"]
|===
|Метод
|Описание

|`withInitializer()`
|Инициализирует новый экземпляр сущности перед открытием экрана деталей. Инициализатор вызывается только в режиме создания, то есть после `newEntity()` или `newEntity(entity)`.

|`withContainer()`
|Задает `CollectionContainer`, который нужно обновить после закрытия экрана деталей с результатом `SAVE`. Если контейнер является вложенным, как описано в xref:data/property-containers.adoc[Контейнеры свойств], фреймворк также инициализирует ссылку на родительскую сущность для новой дочерней сущности и настраивает связь parent-child между `DataContext` для редактирования композиции.

|`withListDataComponent()`
|Задает `ListDataComponent`, например `DataGrid`, из которого фреймворк получает связанный контейнер коллекции, если он не был явно указан через `withContainer()`. После закрытия диалога фокус также возвращается на этот компонент.

|`withParentDataContext()`
|Устанавливает родительский `DataContext` для открываемого экрана деталей. В этом случае экран деталей сохраняет изменения в родительский data context вместо прямого сохранения в data store. Используйте этот метод, когда дочернюю сущность нужно сохранить вместе с мастер-сущностью. Дополнительную информацию смотрите в разделе xref:data/data-context.adoc#parent-data-context[Родительский DataContext].

|`withTransformation()`
|Преобразует сохраненную сущность перед записью обратно в поле, контейнер или list data component.

|`withField()`
|Задает поле, которое получит сохраненную сущность после закрытия экрана деталей с результатом `SAVE`.

|`withAddFirst()`
|Определяет, нужно ли добавлять новую сущность в начало standalone-контейнера коллекции. Для вложенных контейнеров новые элементы всегда добавляются в конец.

|`withViewConfigurer()`
|Позволяет настроить экземпляр открываемого экрана до показа диалога.
|===

Эти методы билдера часто используются при открытии диалогов деталей для дочерних сущностей.

Используйте `withListDataComponent()` или `withContainer()`, чтобы связать диалог с коллекцией, показанной на текущем экране, и `withParentDataContext()`, чтобы влить изменения дочерней сущности в data context родительского экрана.

Точная настройка зависит от модели данных экрана и конфигурации связей между сущностями. Полные примеры смотрите в xref:data-modeling-composition-guide:index.adoc[Composition Guide]. Дополнительную информацию о parent-child data contexts смотрите в разделе xref:data/data-context.adoc#parent-data-context[Родительский DataContext]. Дополнительные примеры доступны в https://demo.jmix.io/ui-samples[UI Samples^].

[[view-inference-conventions]]
== Соглашения о выводе имен экранов

Экран списка или деталей можно вывести из класса сущности.

При переходе к экрану списка с помощью `viewNavigators.listView(this, SomeEntity.class)`, фреймворк выбирает экран в следующем порядке:

. Экран, помеченный `@PrimaryListView(SomeEntity.class)`.
. Экран с идентификатором `SomeEntity.list`.

При открытии экрана списка для поиска с помощью `dialogWindows.lookup(this, SomeEntity.class)`, фреймворк выбирает экран в следующем порядке:

. Экран, помеченный `@PrimaryLookupView(SomeEntity.class)`.
. Экран с идентификатором `SomeEntity.lookup`.
. Экран, помеченный `@PrimaryListView(SomeEntity.class)`.
. Экран с идентификатором `SomeEntity.list`.

При переходе к экрану деталей или открытии его в диалоговом окне фреймворк выбирает экран в следующем порядке:

. Экран, помеченный `@PrimaryDetailView(SomeEntity.class)`.
. Экран с идентификатором `SomeEntity.detail`.
